# [ADR-0003]：[検索PoCでは検索器・質問解析・タグ付けを分離評価する]

## ステータス

採用

## 背景

- 課題：
    - ベクトルRAG、BYOG GraphRAG、LLM生成Graphを同時に変更しており、精度が変化した原因を特定しづらい
    - RAGは類似度上位k件、BYOGはGraphで到達した全案件を返しており、現在の評価条件は揃っていない
    - BYOGは質問内の複数条件をANDせず、複数起点の案件集合を和として返している
    - Graph検索結果に関連度順位がなく、本番でユーザーへ提示する上位案件の品質を評価できない
    - 質問理解、Graph検索、案件タグ付けを一度にLLMへ任せると、失敗原因とAPIコストを切り分けられない
    - 合成案件・質問・正解・オントロジーが同じ開発文脈で作られており、本番精度をそのまま証明できない
- 制約：
    - PoCでは、案件情報の横断検索がキャリアの選択肢を広げられるかを優先して確認する
    - LLM Graphの再構築とコミュニティ要約にはAPI費用と待ち時間が発生する
    - ADR-002で、参画可能性、ジュニア可否、空き状況、個人とのマッチ度は対象外としている

## 意思決定

- 検索PoCを次の順序で分離して評価する
    1. 人が作った理想的な検索計画を使い、RAG / BYOG / Hybridの検索性能を評価する
    2. 自然な質問からLLMが同じ検索計画を生成できるかを、hold-out質問で評価する
    3. 新規案件を固定オントロジーへ制約付きでAIタグ付けできるかを、hold-out案件で評価する
    4. 合成データで方式を固めた後、実案件と対象ユーザーの質問で最終確認する
- PoCの最初の比較対象はベクトルRAGとBYOGとする
    - LLMが自由生成するGraphは、評価形式と検索結果のインターフェースが固まるまで再調整を保留する
    - これにより、評価基準の変更ごとにClaudeでGraphを再生成するコストを避ける
- 自然な質問文と検索計画を分離する
    - PoCの検索計画は人が正解として作成する
    - 検索計画は `exact / filter / graph_expand / graph_bridge / global_summary` 等のmode、AND / OR、条件、起点ノード、対象関係を持つ
    - PoC後半では、この検索計画をLLMが制約付きJSONとして生成する
- 検索器の比較条件を揃える
    - 同じ案件、質問、正答案件ID、案件文、Titanモデル、k、評価コードを使う
    - BYOGはGraphで候補案件を取得し、Gを優先して同じGの候補内をTitan類似度Vでrerankする
    - RAGは全案件をTitanで順位付けする
    - `k=5 / 10 / 20` で `Precision@k / Recall@k / F1@k / nDCG@k` を測る
    - 正答案件がない質問は通常質問の平均へ混ぜず、No-answer accuracyとして別集計する
    - 方式調整に使う `development` と、構成固定後に一度だけ評価する `holdout` を分離して集計する
    - rerank前のCandidate Recall / Precisionを出し、候補漏れと順位不良を分離する
    - BYOGはGraph-first＋V同点解消の通常順位とは別に、GだけのGraph-only順位を出し、Titan同点解消の効果を比較する
    - 全体平均だけでなく、事実引き・横断・周辺・全体像・該当なしの分類別に集計する
    - 候補全体のRecallと、ユーザーへ提示する上位k件の品質を分けて評価する
- 本番候補は、結果に応じてHybrid構成を検討する
    - 明確な事実・属性条件は構造化検索またはRAG
    - キャリア周辺・隣接業務はBYOG
    - BYOG候補の提示順はGraph関連度を優先し、同じ関連度の中をTitanで決める
    - 全体像質問だけコミュニティ要約を使う
- BYOGの本番運用では、上位構造を人が管理し、新規案件のタグ付けをAIで補助する
    - 職種、業務・能力、スキル、ドメイン、クラウドの型を維持する
    - AIは既存ノードへのタグとconfidenceを返す
    - 未知概念、新しい職種名、低confidenceだけ人がレビューする
- PoCの詳細、暫定成功基準、実装課題は `docs/poc/rag-vs-graphrag.md` を正本とする
- 各検索方式とCLI引数の実際の挙動は `docs/poc/検索方式とCLI引数.md` に記録する

## PoCで評価すること

- Graphが必要な周辺・キャリアブリッジ質問で、同じkのRAGよりBYOGまたはHybridが改善するか
- BYOGが、共通スキルを持つだけの無関係案件を除外できるか
- 横断条件をANDとして処理できるか
- Graph関連度を保ち、同じ関連度の中をTitanでrerankした上位案件が、ユーザーに提示できる品質か
- 該当なしを適切に返せるか
- Graph経路を「なぜこの案件が出たか」として説明できるか
- LLMが自然な質問から正しい検索計画を生成できるか
- LLMが新規案件を固定オントロジーへタグ付けできるか
- BYOG / RAG / LLM Graphの初期構築費用、差分更新費用、検索費用、待ち時間
- 実案件で、対象エンジニアが知らなかった妥当な隣接案件を発見できるか

## PoCで評価しないこと

- 案件と個人のマッチングスコア
- ジュニアが参画可能か、現在参画可能かの判断
- キャリア実現確率、スキルギャップ、学習計画
- Slack / Gmail / 音声の本格ETL
- Graph DB、認証、権限、リアルタイム更新を含む本番基盤
- 本番UI、ストリーミング回答、運用監視基盤
- 完全なMicrosoft GraphRAGの再実装
- すべての質問分類でGraphRAGがRAGより勝つこと
- LLM Graphの再生成を繰り返し、偶然精度が上がる構成を探すこと

## 判断

- 周辺検索でBYOG / Hybridが同じkのRAGを明確に上回り、AIタグ付けの精度・コストも許容できる場合：
    - 固定オントロジーを使うHybrid検索を本番候補とする
- 事実引きではRAG、周辺検索ではBYOGが強い場合：
    - 質問モードを分けるHybrid検索を本番候補とする
- 同じkでRAGとBYOGの差が小さい場合：
    - RAGを優先し、Graphの維持コストを負わない
- 両方式が実データで低精度の場合：
    - 検索方式ではなく、案件情報の不足・表記ゆれ・タグ品質を先に改善する
- 人手検索計画では高精度だがLLM検索計画で低下する場合：
    - Graphではなく質問解析を改善し、必要に応じて確認質問を導入する
- AIタグ付けの精度が低い、または人手レビュー率が高い場合：
    - BYOGの自動運用を見送り、オントロジーを縮小するかRAG中心へ切り替える

## 結果・影響

- メリット：
    - 検索器、質問理解、タグ付けの問題を分離できる
    - RAGとGraphRAGを同じ表示件数・順位指標で比較できる
    - LLM Graph再生成による不要なAPIコストを抑えられる
    - BYOGの精度だけでなく、本番で維持可能かも判断できる
    - PoCの終了条件と、RAG / Graph / Hybridの採用条件が明確になる
- リスク/負債：
    - 手動の検索計画作成に一時的な工数が必要
    - 理想的な検索計画での精度は、自然言語入力を含む本番精度より高くなる
    - Graph-first＋Titan同点解消、AND / OR、nDCG、埋め込みキャッシュ、development/holdout分離の実装は追加済みだが、検索計画の承認とholdout・実データでの評価が必要
    - 合成データだけでは最終判断できず、実案件と人が作った質問が必要
- 影響：
    - 次の実装はLLM Graphの改善ではなく、RAG / BYOG共通評価、検索計画、Titan rerankを優先する
    - PoC Aが成功するまで、質問解析エージェントや案件タグ付け自動化の本格実装を開始しない
    - 最終的な方式採用は、本ADRではなくPoC結果を受けた後続ADRで決定する
